vLLM Toolchest — Help

A manual for running local LLMs on the vLLM inference engine, wrapped in a web UI.

Quickstart

  1. Download a model. On Download Models, search HuggingFace and pick a repository. Unlike GGUF tooling you download a whole repo, not one file — an FP8 or AWQ checkpoint is several files that only work together.
  2. Make it active. On Models, click the radio button beside it. vLLM serves one model per process, so this is a choice among models, not a set of them.
  3. Check it fits. The VRAM est. column estimates the memory that model needs at its configured context length. If it says the model needs more than you have, lower Context length in Configure before you start.
  4. Start the engine. On Server, click Start. Loading takes anywhere from twenty seconds to several minutes; watch the log panel.
  5. Send a request. Use the OpenAI-compatible endpoint on the Server page, passing the name from /v1/models in the model field.

Core concepts

One model per process

vLLM is not a router. A vllm serve process loads exactly one model, and switching models means stopping that process and starting another. There is no "enabled" set and no on-demand loading: the active model is the one the engine is serving, and everything else is inert on disk.

That makes a restart expensive in a way worth planning around. Stopping frees the GPU immediately, but starting again re-reads the weights, re-allocates the KV cache, and re-captures the CUDA/HIP graph ladder. A restart glyph (↻) appears beside a model on the Models page when it is the active one but not the one currently running — that is the UI telling you a restart is owed, not that something is broken.

Every setting in Configure is an engine-launch parameter. None of them can be changed on a running server — they take effect at the next start. The UI never pretends otherwise.

gpu_memory_utilization and the pre-allocated KV cache

This is the setting that surprises people coming from llama.cpp. vLLM does not grow its KV cache as requests arrive. At startup it measures free VRAM, multiplies by gpu_memory_utilization, subtracts the model weights and activation overhead, and claims all the rest as one fixed KV-cache pool. That pool is the entire budget for concurrent requests and context for the life of the process.

Two consequences:

  • The fraction is of total GPU memory, not of what is free after your desktop compositor. On a card also driving a display, 0.90 can be more than is actually available.
  • Raising it does not make the model faster; it buys concurrency and context. Lowering it is the first thing to try when a start OOMs.

max_model_len and the context probe

--max-model-len sets the longest sequence the engine will accept, and because the KV cache is sized from it, it is usually the parameter that decides whether a model loads at all. A model whose config advertises 262,144 tokens will happily refuse to start at that length on a 24 GB card.

Rather than bisecting by hand, use Probe maximum context on the Benchmarks page. It binary-searches the largest --max-model-len that actually starts, by starting the engine for real at each candidate and watching for readiness or an out-of-memory failure. Steps are 256-token multiples because that is vLLM's KV-cache block size — finer increments produce identical outcomes. A probe takes a while for the same reason a start does: each trial is a real load.

Tensor parallelism

--tensor-parallel-size splits a model's weights across several GPUs, so each holds a fraction of the parameters and a fraction of the KV cache. It is how a model larger than one card gets served at all. TP must divide the model's attention head count evenly, and every layer's output has to be summed across the GPUs — an all-reduce — on every forward pass. That communication is the cost: two GPUs do not give you twice the speed, and on consumer boards without fast peer-to-peer links they can be slower than one.

The all-reduce token ceiling (radiance image)

The radiance image replaces the all-reduce with a hand-written peer-to-peer kernel, and that kernel takes a message only up to 48 MiB. A prefill chunk's message is max_num_batched_tokens × hidden_size × 2 bytes, so there is a per-model ceiling on the batched-token setting above which the custom kernel stops being used.

Exceeding it is silent. Nothing errors, nothing is logged; vLLM falls back to RCCL at roughly 2.3× the cost and everything keeps working. This is why the model config panel computes the ceiling for the model in front of you and shows it under the batched-token field — it is not information you can recover from the logs afterwards.

The ceiling only applies at TP=2, which is the only world size the shipped kernel library handles. At TP=1 there is no all-reduce, and at TP=4 or more RCCL is used regardless, so the panel says so rather than showing a number that does not apply.

{{end}}

Served model names

The name a client passes in the model field is the model's HuggingFace repo ID — cyankiwi/Qwen3.5-4B-AWQ-4bit — the same identifier the Models page shows. Every launch passes it to vLLM explicitly; left to itself vLLM names a model by the path it was loaded from, and a client would have to send a container-local path.

/v1/models reports the model being served, and nothing else. vLLM serves one model per process, so the list is one entry or none — an empty list means nothing is loaded, not that nothing is installed. Use the Models page to see what is available to load.

Quantization formats

Quantization does two different jobs, and conflating them causes most of the disappointment:

FormatWhat it doesOn RDNA4 (gfx1201)
fp88-bit weights and activationsAccelerated — the matrix units execute FP8 directly. Halves weight memory and speeds up compute.
awq, gptq4-bit weights, 16-bit activationsWeight-only. Quarters weight memory, but the weights are dequantized before the matmul, so compute runs at bf16 speed. Buys VRAM, not throughput.
compressed-tensorsA container, not one schemeDepends what is inside — it may hold an FP8 w8a8 checkpoint or a 4-bit weight-only one. The Models page shows the detected width beside it.
mxfp4, nvfp44-bit block floating pointNewer formats with hardware support on some parts. Treat performance as something to measure rather than assume.
bitsandbytes4-bit weights, on-the-flyOnly offered when the library is present in the image. Convenient, consistently the slowest option.

The short version: FP8 for speed, 4-bit weight-only for fit. If a model already fits comfortably, a 4-bit quant of it will not be faster.

Server

The dashboard and the engine controls are one page. It carries:

Server card
Start, Stop and Restart, the current state, and the model picker. The picker sets the same active model the radio buttons on the Models page do — they are one setting seen from two places.
GPU
Per-GPU utilization, VRAM, temperature and power, read from the kernel driver rather than a vendor library. On a multi-GPU box each card is listed by its own index.
Models, API Endpoint
How many models are registered, and the base URL to point an OpenAI-compatible client at.
Live Performance
Tokens per second and time-to-first-token for requests as they are served, so you can see the engine working without running a benchmark.
Logs
The engine's stdout and stderr, streamed. This is the only place a failed load explains itself — read it before anything else when a start does not finish.

Models

One row per registered model. Columns are the model's name and repo ID, its quantization method and bit width, an estimated VRAM figure, and its size on disk.

The radio button
Makes a model active — the one Start will launch. Choosing a different one while the engine is running does not switch models; it marks a restart as owed and shows the ↻ glyph.
VRAM est.
Weights plus KV cache at the configured context length plus activation overhead, with a verdict — fits one GPU, needs two, or too large. It is an estimate from the model's own config, computed two ways with the larger winning, because the structural formula undercounts hybrid and mixture-of-experts models. Treat it as a planning figure, not a guarantee.
Configure
Opens the launch config for that model, inline. See below.
Remove
Unregisters the model, with the option to delete its files. Removing the registry entry alone leaves the files to be found again by the next scan.
missing
The registry has an entry whose files are gone. It cannot be served, and the radio is disabled.

Model config

Every field here becomes a vllm serve flag, shown in full under Effective command at the bottom of the panel — worth reading once, because it makes the mapping between this UI and vLLM's own documentation obvious.

Core
Data type, context length, tensor parallel size, and GPU memory utilization — the four settings that decide whether the model loads.
Performance
Eager mode (skips graph capture: faster to start, slower to run), prefix caching, chunked prefill and the batched-token budget, and maximum concurrent sequences.
Quantization
The detected method and the KV cache data type. Setting the KV cache to fp8 roughly halves cache memory, which buys context length at little quality cost.
Tool Use
OpenAI-style function calling and the parser to use. The parser is auto-detected from the chat template; override it only if detection got it wrong.
Advanced
Speculative decoding config, compilation config, attention backend override, and a free-text flags box for anything this UI does not model.
Context length offers the model's advertised maximum and a custom box. The advertised maximum is what the model was trained for, not what your card can hold — use the context probe to find the second number.

Download Models

Search HuggingFace and download whole repositories. The format filter is worth understanding: it queries the Hub for the format's tags rather than filtering results after the fact, so a filtered search reaches models a plain search would not have returned in its first page.

Detected formats are read from each repo's own quantization_config where it has one, falling back to its tags and then its name. That ordering matters — a repository named ...-FP8 that actually holds a 4-bit compressed-tensors checkpoint is labelled by what is inside it.

Disk space
Free space is checked against the download size before starting, with a 2 GiB safety margin, and in-flight downloads are counted against it so two downloads started together cannot both "fit".
Interrupted downloads
Cancelling leaves .part files rather than deleting them, and a resumed download continues from where it stopped. Incomplete downloads are listed with the space they occupy so you can reclaim it deliberately.
Gated models
Llama, Gemma, Mistral and others need a HuggingFace token, set in Settings, plus acceptance of the licence on the model's own page.

Benchmarks

Four things live here: ad-hoc runs, batch jobs, the context probe, and the comparison and visualization views.

Presets

internal-quick
One request, 512-token prompt. A sanity check after a load — about 15 seconds.
internal-standard
Three repetitions across 128 / 512 / 2048-token prompts. Shows how prompt length affects time-to-first-token.
internal-thorough
Five repetitions across four prompt sizes up to 8K. What to use for a number you intend to quote.
internal-long-ctx
A single 32K-token prompt. Stresses the KV cache and paged attention rather than raw generation.
benchy-*
Runs through llama-benchy, an engine-agnostic harness. Use these when you want a number comparable with a llama.cpp measurement; the concurrency preset sweeps parallel requests to find where continuous batching stops scaling.

Batch jobs and sweeps

A batch job runs every combination of the models and presets you tick. Cells are grouped by model so each model is loaded once rather than once per preset.

Sweep parameters multiply that out: context length, tensor parallel size, GPU memory utilization, concurrent sequences, KV cache dtype and eager mode. Each is an engine-launch parameter, so every combination is a separate model load — three context lengths across two models is six loads, not six requests. Jobs are capped at 64 combinations for that reason.

What is measured, and comparing runs

Generation tokens per second, prompt (prefill) tokens per second, and time to first token, each averaged across repetitions. Select several runs and Compare shows only the dimensions that actually differ between them, so a table of ten runs that vary in one parameter has one column rather than twenty.

Visualize plots the same data: scatter, leaderboard, heatmap, faceted heatmaps, a Pareto view of prompt speed against generation speed, parallel coordinates, and two 3D views. Charts that need two varying parameters are offered only when two exist. Where several runs share a configuration their measurements are averaged; a combination never run is left as a gap rather than drawn as zero, because zero is a measurement and would colour as the worst result.

Tuning

An autotuner for block-FP8 GEMM kernels. For a chosen model and tensor-parallel size it derives the unique weight-matmul shapes that model's decoder layers will execute, benchmarks kernel configurations for each, and writes the winners as JSON files that vLLM loads at run time.

Two things to know:

  • It only helps models with block-quantized FP8 weights. Other formats never reach the kernel being tuned.
  • Tuned configs are keyed by the device name vLLM reports, not by the marketing name or the architecture. That name is probed from the running vLLM at startup rather than guessed, because the image variants disagree about it — and a file written under the wrong name is correctly formatted and never read. The name in use is shown in Settings under Environment.

Settings

API & Connection
The external URL shown to clients, an optional API key required as a Bearer token on /v1/*, and the HuggingFace token used for gated downloads.
vLLM Defaults
Applied to newly downloaded models. Changing them does not touch configs that already exist.
Process Management
Auto-restart on crash, and auto-start on container startup. Auto-start launches the active model in the background after the web UI is already listening, so a model that fails to load leaves you a log to read rather than an unreachable server.
Runtime environment
Environment variables applied to the vLLM process, taking effect at the next start. The curated table is short on purpose — vLLM defines nearly 300 variables, most for hardware or topologies this tool never runs on. The Extra environment box takes anything else, one KEY=VALUE per line, and applies last. Variables that fight a mechanism this tool depends on (device-visibility overrides, HSA_OVERRIDE_GFX_VERSION, HuggingFace cache paths) are saved with a warning rather than refused.
These are applied after the container's own environment, so a value set here replaces what the image exports — the opposite of how the equivalent works in llama-toolchest. The Effective environment preview marks every line that overrides an image value.
{{if .IsRadiance}}
Radiance
The RDNA4 image's feature switches. Every one defaults to image default, which leaves the image's own value alone rather than pinning one here that would then drift as radiance is updated. These are applied after the runtime environment, so the switch you can see wins over a RADIANCE_* line typed into the extra box.
{{end}}
Backup & Restore
Exports settings, the runtime environment, the Radiance switches and every model's launch config as one versioned JSON file. Model configs are keyed by HuggingFace repo ID rather than by path, so a backup restores onto a different machine; a config for a model not installed there is held as pending and attaches by itself when that model is downloaded, however much later. Restore is per-section and is a merge — it never deletes. Tensor parallel size is reduced to fit the target's GPU count, with a warning, because a config asking for more GPUs than exist fails minutes into a load rather than at restore. Secrets travel only via the explicit checkbox, in plaintext. Deployment identity (listen address, ports, paths) is recorded for reference and never applied. For scripting: GET /api/backup (add ?secrets=1) and POST /api/restore. Benchmark history is not included — export that from the Benchmarks page.
Storage
The data directory is set at install time and shown for reference. The models directory can be pointed elsewhere — an absolute path to an existing directory inside the container, which means a mounted volume. Restart after changing it: the registry and the downloader read it once, at startup.
Theme
Applied immediately in this browser and saved as the default other browsers start from.

Using the API

The engine speaks the OpenAI /v1/* dialect and this tool proxies it, so any OpenAI-compatible client works.

curl $BASE/v1/models

curl $BASE/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<name from /v1/models>",
    "messages": [{"role": "user", "content": "hello"}]
  }'

If an API key is set in Settings, add -H "Authorization: Bearer $KEY". The key guards /v1/* only — the management API under /api is same-origin and protected by your network posture, so treat access to this UI as administrative access.

There is no on-demand loading. A request for a model that is not the running one is not a cue to switch; it is an error.

Troubleshooting

Start fails with an out-of-memory error
In order of what to try: lower Context length, set the KV cache dtype to fp8, lower GPU memory utilization, or raise tensor parallel size if you have another GPU. Use the context probe to find the real ceiling instead of guessing.
Start hangs, then times out
Usually graph capture on a large model. Read the log panel — the last line says which stage it reached. Enabling Enforce eager mode skips capture and starts faster, at some steady-state cost.
The model loads but is much slower than expected
Check what the quantization is actually buying you: a 4-bit weight-only checkpoint runs its matmuls at bf16 speed. On the radiance image at TP=2, also check the batched-token setting against the all-reduce ceiling shown in the model config panel — exceeding it costs about 2.3× and reports nothing.
/v1/models is empty
Nothing is loaded. The listing reports what is being served, not what is installed — it is deliberately not a catalogue, because a name listed there that no request can be served by is worse than an empty list. Make a model active on the Models page and start the engine.
A request is rejected with an unknown model
Pass the repo ID exactly as /v1/models reports it. An engine started before this tool set the served name — or started by hand — will still be answering to its file path instead; restarting it from the Server page fixes that.
A downloaded model is not on the Models page
If the models directory was overridden without a restart, the scan is still reading the old path. Restart the container.
Tuned kernels seem to have no effect
They are keyed by the device name vLLM reports. Confirm the name in Settings → Environment matches the one the tuned files were written under; a mismatch produces correctly-formatted files nothing ever reads.
A setting will not stay changed
Engine-launch parameters apply at the next start, not immediately. If the Models page shows the ↻ glyph, a restart is owed.
